# Recognition cleanup dependency and deletion audit

Audit starts at `main.py --profile event-driven --identity-mode lightweight`, not a B16 execution-only trace. Working tree already contained unrelated damage/inference/UI work plus the untracked double-faint implementation; those edits and every saved benchmark remain in place. No commit/staging/push. [Direct import inventory](import-inventory.md) records source callers, including function-local imports, across 401 Python files in explicit source/test directories; caches and generated outputs were excluded. Targeted call/CLI/test searches and B16's manifest/frozen source supplement those edges.

No entire OCR adapter/scheduler or old processing file was deleted merely because B16 did not exercise it. All retained adapters have executable callers or explicitly uncertain compatibility obligations. This is a scoped consolidation, not a wholesale renaming of milestone modules.

## Compatibility boundaries

Raw evidence/event/state schemas, slot assignment, cross-battle ownership and tracking policy remain unchanged. Acquisition source/config fingerprint changes require a fresh run ID. The strict `--reconstruct-from` compatibility check intentionally remains strict; frozen evidence is validated read-only with `verify_recognition_cleanup.py`, not relabeled as newly acquired OCR. Existing exact OCR cache hashes for unchanged model/crop implementations remain usable. A 3-FPS run must use a matching frame grid; a 2-FPS cache cannot masquerade as a 3-FPS acquisition.

Double-faint scheduling changes only when expensive verification is attempted. It never binds slots. It conservatively admits candidate hints to the original full engine and leaves unknown routing unresolved. Genuine candidates still require the original atomic bijective independent HUD proof. Remaining full prefix replay for genuine candidates and development-mode replay cost are documented limitations, not hidden performance guarantees.
