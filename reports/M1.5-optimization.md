# M1.5 performance optimization — 2026-10-14

Focused follow-up: [separate HUD, move, message, party/replacement, and target ROI detection at 5 fps / nominal 3 fps](M1.5-focused-rois.md). It is an isolated experiment; conservative production detection remains unchanged.

Adaptive monitoring and scheduling, a bounded live capture adapter, and an opt-in ONNX/Core ML backend are implemented. The existing Paddle CPU backend remains the default. **The production P95 ≤ 1-second decision completion target is not met.** Measured improvements come with explicit scope and uncertainty limits; no lossless production message-recall claim is made.

The original [M1.5 validation](M1.5-streaming.md), its approximately **18.506-second P95**, and original traces remain intact. All experiments below reuse the existing 110 cached frames from the 178–200-second battle interval. No video was decoded or reprocessed, no 10 fps evidence was fabricated, and no M2 state reconstruction, strategy, damage calculations, game automation, commit, or push was added.

## Implementation and reliability

`MonitoringRates` separates acquisition, periodic phase checks, message monitoring, routine field checks, icon checks, stable-field refresh, and the optional message OCR budget. Defaults are 5/2/5/2/1 fps, a two-second stable-field refresh, and a 16-crop candidate ring. These are periodic scheduling rates, **not hard maximums**: changes to normalized message/HUD/condition/control ROIs override periodic deadlines. A short control or message change is inspected even if the previous phase was animation. Unsupported/unknown phases keep the independent message probe and conservative uncertainty.

The ROIs reuse validated recognizer geometry: lower message band, two own and two opponent HUDs, condition banner, and decision controls. They scale with image resolution. The HUD crops include identity/HP/status pixels; status, fainting, weather, terrain, and transformation effects are **not interpreted as events**. Off-HUD identity changes and unvalidated indicator layouts remain limitations. Additional target-card names/HP, selected-move banners, and party names/HP are opt-in through the adaptive planner. The regions were checked against original target/party fixture layouts; their full OCR accuracy is not established by bounding-box tests.

Routine fields reuse exact raw crops or the existing exact light-glyph masks, with periodic rechecks. Adaptive reuse can cross compatible UI phases without replaying the same static field. Message coalescing still requires exact raw pixel identity; no scene-similarity or minimum-language/character rule merges messages. The remaining legacy screenshot recognizer's five-Chinese-character acceptance cutoff was also removed. Confidence rejection retains raw OCR and validation reasons.

The optional `--message-ocr-fps 2.5` policy samples expensive reads on changed message versions, with immediate phase-entry reads. It **does not assume** a minimum display duration or merge typewriter stages into a confirmed sentence. Every deferred version is an unresolved, timestamped, PNG-backed candidate with a stable ID, delivered in both capture-ordered full bundles and the independent ordered message lane. A dark/occluded/no-white candidate also stays unresolved. Exact duplicate evidence is reused before applying this budget. Skipped recognition makes readiness uncertain; it cannot become ready simply because worker queues drain. A one-frame message may remain available only as a candidate crop, so this budget is experimental and is not the default.

`LiveCapture`/`run_live` use a separate acquisition/ROI-monitor thread and a bounded full-frame queue. Recognition backpressure does not stop this thread from inspecting acquired frames. Changed message, HUD, condition, and **control** crops are delivered to the evidence sink before queued full frames can be evicted. An evidence sink must drain promptly and archive those records; the in-memory crop ring is intentionally finite. Queue loss, capture/sink deadline misses, interruptions, and source errors are explicit and propagate coverage uncertainty. Source-end acquisition thinning is also reported. Reusable camera buffers are frozen, and actual acquisition monotonic clocks are preserved rather than overwritten by replay dispatch clocks.

Decision watermarks now include move, target, party, and replacement selection interfaces. This establishes a processing barrier for visible decision UI, not a chosen move, switch commitment, turn boundary, or strategy. A prior settled watermark does not cover newer unclassified frames in the live capture queue; consumers must also track capture/control candidate IDs and pending/loss records. These added opportunities change the decision sample population relative to the original four-ticket benchmark.

## Controlled paced replay results

One warm model per experiment group, no icons, same existing 5 fps cache, sequential trials. These are single development trials with shared/cache warming and uncontrolled host load, not statistical performance guarantees. Source timestamps have 0.2-second grid uncertainty. Throughput is accepted frames divided by total wall time, including final drain. All runs ultimately settled `uncertain`.

| Configuration | Input frames | OCR calls | Wall time | Throughput | Decision completion P95 | Peak queued jobs |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A: Paddle CPU, existing 5 fps policy | 110 | 349 | 42.995 s | 2.558 fps | 19.640 s (4 tickets) | 46 |
| B: fixed 2 fps, same CPU policy | 44 | 205 | 25.736 s | 1.710 fps | 3.526 s (2 tickets) | 53 |
| C: conservative scheduling, same field scope | 110 | 315 | 41.017 s | 2.682 fps | 18.385 s (4 tickets) | 37 |
| C: optional OCR budget, same field scope | 110 | 278 | 31.909 s | 3.447 fps | 8.988 s (4 tickets) | 24 |
| C: expanded decision regions, full message reads | 110 | 435 | 53.453 s | 2.058 fps | 24.457 s (4 tickets) | 45 |
| C: final expanded regions + OCR budget | 110 | 389 | 39.201 s | 2.806 fps | **15.281 s (6 tickets)** | 37 |
| D: ONNX medium/Core ML, existing sampling | 110 | 349 | 61.176 s | 1.798 fps | 40.341 s (6 tickets) | 56 |
| E: Core ML + OCR budget, original field scope | 110 | 278 | 44.171 s | 2.490 fps | 23.326 s (6 tickets) | 51 |

Changing only conservative scheduling reduces OCR calls by 9.7% and wall time by 4.6%. With the experimental budget at unchanged field scope, calls fall 20.3%, wall time falls 25.8%, and throughput rises about 34.7%. Expanded decision coverage has a real cost: it adds fields and probes, so it is reported separately. Against expanded full-message recognition, the final budget run reduces wall time by 26.7% and increases throughput about 36.4%. Candidate-only versions are **not counted as OCR calls**. Smaller decision samples, missing captures, and changed watermark coverage must not be mistaken for a proven latency improvement on identical decision opportunities.

The final expanded run performs 389 OCR calls, including 60 message reads, and emits 50 unresolved message candidates (46 budgeted versions and four no-white probes). The 16-crop ring evicts 34 old entries after sink delivery; the trace retains their pixels. All 110 frames are accepted, with four in-flight frames at peak and no captured timestamp gaps. OCR service totals **37.717 seconds of 39.201 wall seconds**, so CPU OCR remains dominant.

Final P50/P95/worst ordered availability is **1.346/15.281/17.990 seconds**. Message-lane availability is **1.346/13.621/15.657 seconds**, including unresolved candidates; it is not a distribution of successful OCR alone. Decision completion is **5.513/15.281/15.281 seconds** over six tickets. Producer dispatch lateness is **0.875/12.632/14.824 seconds**. Peak process RSS is approximately 1.4 GB; shared-model trials report cumulative high-water RSS, not incremental model memory. These figures plainly fail sustained 5 fps and the one-second target.

Sources: [CPU comparison](M1.5-adaptive-performance.json), [budget isolation](M1.5-adaptive-budget.json), [final expanded run](M1.5-adaptive-final-v2.json), [Core ML paced comparison](M1.5-coreml-performance.json). Earlier development variants are retained rather than rewritten.

## Detector and accuracy evidence

Five messages are now visually transcribed from actual cached images: transformation, move execution text, flinch text, Dragon Dance text, and the attack/speed increase text. Fixture checksums and [annotations](../tests/fixtures/m15_adaptive_ground_truth.json) are recorded. These are five reviewed points, **not an exhaustive message inventory or a holdout set**.

A and conservative C recognize all five reviewed timestamps exactly. B and budgeted C recognize four of the five exact timestamps, while finding all five reviewed text strings elsewhere in the clip. At **182.4 seconds**, budgeted C preserves an unresolved flinch-message crop and reads matching text at 182.6 seconds. This delayed text is reported separately; it does not relabel the reviewed point. Fixed 2 fps also drops 66 input samples and loses decision-interface re-entries: its lower latency is not a reason to adopt it.

The ROI detector takes about **6.4 ms median / 6.7 ms P95** in a standalone cache scan. Animated scenery changes monitored pixels on every frame: all 110 frames trigger phase/routine guard checks despite the nominal 2 fps periodic rate. Thus this clip **does not demonstrate a reduction to 2 fps classification**. Raw and white-mask message fingerprints both change 110/110 times; a connected-component experiment changes 107/110 times and was not adopted. Background animation remains a substantial false-trigger source. Full detection precision/recall cannot be calculated from five sparse text labels.

Under CPU OCR load, monitoring plus planning has roughly 0.34-second median / 0.65-second P95 service time in the final run, much higher than standalone monitoring. This exposes scheduling/contention overhead that still needs profiling; it is not evidence that phase classification itself takes 0.65 seconds. No perceptual threshold or fixed debounce was adopted to hide that cost.

The [read-only audit](M1.5-adaptive-validation.json) verifies ordering, IDs, fixture hashes, candidate PNG roundtrips, completed-job accounting, and uncertain final readiness across every experiment. The legacy M1.4 classifier is unchanged; canonical identity resolution and existing regressions remain compatible.

## Apple Silicon acceleration investigation

Paddle's documented macOS backend is CPU-only; CUDA support is not an Apple Silicon acceleration path. ONNX Runtime 1.23.2 on this machine exposes Core ML, and the published PP-OCRv6 medium/tiny ONNX assets are pinned by source revision and SHA-256. They are downloaded only by an explicit setup script. Experiments ran in `.cache/m15-accel-venv`; the existing `.venv` was not changed.

The opt-in backend retains the existing `read()` contract and the same BGR resize/normalization, multiline segmentation, dictionary, CTC decoding, confidence thresholds, and canonical resolver. It never silently labels CPU fallback as accelerated execution. Core ML logs show **17 fused Core ML partitions and 24 CPU nodes**, with unsupported/dynamic operations including a Concat input case. Compute-plan logs assign operations to the **Apple M1 Pro GPU**. Provider profiles confirm both Core ML and CPU work. **ANE-only execution is not established.** Dynamic shapes and partition boundaries are a plausible overhead source, not an isolated causal measurement.

The same deterministic **26 labeled crops** cover five species names (including 赛富豪), four moves, four HP/stat numbers, four abilities, four items, and five messages. Exact accuracy and CER are measured on raw text; accepted/rejected text and confidence are also retained.

| Backend | Exact / 26 | CER | Total region service | Region P95 | Startup | Peak RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Paddle medium CPU | 26 | 0 | 3.035 s | 0.356 s | 2.496 s | 0.978 GB |
| ONNX medium CPU | 26 | 0 | 2.969 s | 0.349 s | 0.540 s | 0.543 GB |
| ONNX medium Core ML | 26 | 0 | 5.424 s | 0.705 s | 7.018 s | 1.204 GB |
| ONNX tiny CPU | 22 | 0.028 across all characters | 0.202 s | 0.023 s | 0.186 s | 0.274 GB |

Tiny recognizes only **2/5 messages exactly**, inserting extra characters in three, and misreads 威吓 as 成吓. Its message CER is 0.039; ability accuracy is 3/4. It is unsuitable as a default replacement despite its speed. The medium backends' 26/26 result is encouraging but does not establish general game OCR accuracy.

For 21 independent single-line crops, medium ONNX CPU batch 1/4 takes **1.307/0.982 seconds** (16.1/21.4 regions/s), with 21/21 exact matches. Tiny batch 1/4 takes **0.080/0.057 seconds**, both 20/21 exact. Core ML batch 1/4 takes **2.138/2.988 seconds**, both 21/21 exact. Multiline message batching also fails to improve the medium CPU aggregate: total region service increases from 2.969 to 3.808 seconds with batch size four. Batching is supported and measured, but is not enabled by default or advertised as a universal win.

The initial Core ML smoke message took 2.745 seconds, including first-shape work; the later corpus message P95 is 0.720 seconds. Warm/shape-cache behavior matters. Core ML's slower full paced trials D/E confirm that correctness and partial GPU execution do not make it a useful production speedup here. Native Core ML conversion was not pursued into a new architecture/weight port: Apple's supported conversion workflow targets TensorFlow/PyTorch, whereas the available local model is Paddle/ONNX. The already functioning Core ML EP provides a practical negative result without an unsupported conversion detour.

Sources: [Paddle macOS support](https://www.paddlepaddle.org.cn/documentation/docs/en/install/compile/macos-compile-make_en.html), [Core ML provider options/limitations](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html), [Apple conversion API](https://apple.github.io/coremltools/docs/source/coremltools.converters.convert.html), [runtime/compute-plan evidence](M1.5-coreml-probe.json), and the `M1.5-ocr-*.json` crop reports.

## Live adapter validation

The initial fake-camera stress test acquired/monitored 110 cached frames with actual acquisition clocks while OCR was backlogged. It averaged 4.267 fps against 5 configured fps, reported 12 acquisition/sink deadline misses, and evicted 23 queued full frames. All changed message/HUD/condition crops were archived. A new regression revealed that controls crops also needed preservation; that omission was fixed and a second stress run is recorded separately.

After controls preservation, the second run acquires/monitors all 110 inputs at **3.531 fps**, accepts 93 for recognition, and reports **17 full-frame evictions and 23 deadline misses**. Wall time is 38.236 seconds, accepted throughput 2.432 fps, and P95 decision processing completion **7.326 seconds over five tickets**. Peak RSS is 1.505 GB. All **770 changed ROI crops**, including 110 control crops and 110 message crops, are archived and checksum-verified. This added reliability has a measurable acquisition/sink cost; ROI encoding and persistence now also need profiling.

The latest results are in [live adapter measurement](M1.5-live-adapter-v2.json) and the [candidate/clock audit](M1.5-adaptive-validation.json). This is a threaded fake camera consuming cached frames, **not phone transport**, and it cannot establish what a real camera would have acquired during missed deadlines. Bounded loss and candidate preservation must not be represented as lossless real-time recognition. The earlier run's shorter P95 over only three decision tickets is especially not comparable to the lossless paced replay's six tickets.

## Reproduce and next steps

Use `.venv/bin/python -m pytest -q` for regressions and `.venv/bin/python scripts/evaluate_m15_adaptive.py` for the saved-evidence audit. Tests cover short/similar messages, ROI changes between periodic deadlines, candidate-budget uncertainty, PNG preservation, source-end gaps, all decision watermarks, frozen camera buffers, acquisition continuing while OCR blocks, queue losses, live source failure, and preservation of real capture clocks. The final full suite passed **179 tests in 61.53 seconds**; the focused streaming/live/monitoring suite passed **48 tests** after the controls preservation fix. One existing Paddle ccache warning remains. `git diff --check` and the saved-trace/crop/clock audit passed.

CPU experiments:

```sh
.venv/bin/python scripts/benchmark_m15_adaptive.py
.venv/bin/python scripts/benchmark_m15_adaptive.py --budget-only --output reports/M1.5-adaptive-budget.json
.venv/bin/python scripts/benchmark_m15_adaptive.py --single-budget --output reports/M1.5-adaptive-final-v2.json
.venv/bin/python scripts/benchmark_m15_live.py
.venv/bin/python scripts/benchmark_m15_ocr.py --output reports/M1.5-ocr-paddle.json
```

Create an isolated acceleration environment, install the project's `ocr_experimental` extra plus runtime/test dependencies there, and explicitly retrieve pinned assets:

```sh
.venv/bin/python -m venv .cache/m15-accel-venv
.cache/m15-accel-venv/bin/python -m pip install -e '.[ocr_experimental]'
.venv/bin/python scripts/setup_m15_onnx.py --size medium
.venv/bin/python scripts/setup_m15_onnx.py --size tiny
.cache/m15-accel-venv/bin/python scripts/benchmark_m15_ocr.py --backend onnx --model-directory .cache/m15-onnx-medium --provider coreml --batch-size 1 --output reports/M1.5-ocr-medium-coreml.json
.cache/m15-accel-venv/bin/python scripts/benchmark_m15_adaptive.py --onnx-directory .cache/m15-onnx-medium --provider coreml --acceleration-only --output reports/M1.5-coreml-performance.json
```

Repeat crop tests with `--provider cpu`, tiny/medium directories, and `--batch-size 1`/`4` to isolate backend/batching effects. These commands regenerate development outputs; use `--output` plus `--trace-directory` for adaptive trials, or `--output` plus `--trace` for live trials, to preserve an earlier trial.

For an opt-in adaptive cached replay, use `stream_replay.py --frames .cache/m15-resolution-178-200/frames.json --adaptive --acquisition-fps 5 --phase-fps 2 --message-fps 5 --routine-fps 2 --icon-fps 1 --message-ocr-fps 2.5 --speed 1 --trace outputs/adaptive.jsonl --report outputs/adaptive.json`. Keep `--message-ocr-fps 5` to avoid budget deferral. Live integration uses `run_live(acquire, pipeline, sink, rates=..., capacity=4)` with a prompt capture callback and durable evidence sink.

Highest-impact follow-ups are: profile CPU recognition and monitor-thread contention; evaluate isolated OCR processes or backend changes on a larger annotated corpus; improve message foreground detection using verified overlays rather than scene similarity; evaluate smaller models only for fields with demonstrated accuracy and safe medium fallback; and test long sustained live capture with actual transport, sinks, and loss accounting. More workers, indefinite model caching, fixed 2 fps acquisition, Core ML/ANE claims, and aggressive debounce are not justified by these results.

The streaming/candidate/loss architecture is functional within the supported observation scope. Adaptive scheduling produces measured gains, but the final expanded CPU replay still takes **39.201 seconds for a 22-second clip**, and P95 decision processing completion is **15.281 seconds** with uncertain evidence. Production real-time performance remains unfinished.
