# M1.5 validation — 2026-10-14

The streaming architecture is functionally complete for the supported captured-evidence scope. The production real-time latency target is **not met**. This is an incremental observation pipeline, not battle-state reconstruction, event confirmation, or strategy. Live phone capture/transport and production message recall remain unvalidated.

## Implementation and regression validation

The existing working tree provides immediate online phase/segment updates, bounded backpressure, one OCR worker with message priority, optional independent icon refinement, capture-ordered full observation bundles, an independent capture-ordered message lane, stable observation IDs, and decision processing watermarks. Replay uses the same incremental path without future-frame smoothing. Exact message-region changes trigger reads; identical evidence can reference an earlier observation. Routine light-text fields use exact glyph-mask reuse with periodic rechecks.

The initial full suite passed 149 tests in 59.63 seconds. After adding validation regressions, the focused streaming suite passed 27 tests. Regressions cover running jobs with empty queues, prior-resolution messages blocking a new decision, out-of-order worker completion, rejected frames, interruptions, recognition failures, unresolved/ambiguous/unavailable icons, frozen frame ownership, bounded buffers, message priority, and message delivery before slow icons. The final full suite passed **158 tests in 60.51 seconds**, with one existing Paddle ccache warning. `git diff --check` passed.

Readiness distinguishes `no_decision`, `pending`, `uncertain`, and `ready`. Outstanding evidence through the decision watermark stays pending; settling unresolved evidence or rejecting a frame preserves uncertainty. Coverage uncertainty is conservative and session-wide, and does not clear merely because queues empty or later reads succeed. A processing latency target boolean measures completion time independently of evidence certainty: it is not permission to act. `ready` only covers captured evidence, never all gameplay events.

## Reviewed messages and length-filter correction

A read-only audit of all four saved traces verifies 110 capture-ordered bundles per run, unique message IDs, 90 message observations per run, completed job accounting, and both manually transcribed messages exactly preserved at 178.0 and 180.0 seconds in that order. The latest trace's 90 independent message-lane IDs match the full-bundle message IDs in order. These are two reviewed text points, not a full-clip recall benchmark. Fixture checksums are verified. See [validation evidence](M1.5-validation.json) and [ground truth](../tests/fixtures/m15_message_ground_truth.json).

Removed the undocumented requirement for at least five Chinese characters. Cached actual UI at 180.0 seconds visibly has two lines, including the four-character move name “击掌奇袭！”; this does not prove a complete four-character message, but rules out treating a short visible text observation as inherently invalid. At 183.8 seconds (`.cache/m15-resolution-178-200/000030.png`), a full flinch message remains visible while OCR returns only “对表的” at 0.715 confidence. Short output can therefore be an incomplete read of real UI, not proof of no message. The reviewed fixtures and clip establish no universal minimum message length, so the rule cannot be justified.

Message acceptance now retains any nonempty backend-accepted text at confidence >= 0.8, with no length/language cutoff. Every result includes explicit validation status/reason; rejected candidates retain raw text and confidence and contribute uncertainty when required or nonempty. Accepted text remains a visible-text observation, not a confirmed complete sentence or gameplay event. Synthetic short-text regressions test policy only; they are not added game ground truth. Confidence alone still admits some erroneous text, as the historical trace shows; confidence calibration and completeness evaluation remain future validation work.

The saved traces contain **zero high-confidence short candidates** that the removed length rule alone would reject. Their accepted outputs remain applicable. Historical benchmark files and timings were preserved unchanged; no new timing measurement is claimed after this correction, and no video was reprocessed.

## Measured performance

Measured on Apple M1 Pro, 16 GiB RAM, Python 3.10.4, PP-OCRv6 medium, one warm OCR instance, four OCR CPU threads. The replay uses 110 cached frames from a 22-second interval at 5 fps; source timestamps are a resampled grid with 0.2-second uncertainty. Initialization in the original comparison took 2.317 seconds. Runs were sequential with shared model/cache warming; they are development measurements, not controlled production comparisons. No phone transport was measured. P95 uses nearest rank; only four decision samples exist per run.

The reported approximately 18.5-second P95 is specifically **decision processing completion** in the latest paced run. Every settled decision is `uncertain`; it is not a P95 of successful decision readiness. Latest independent message-lane P95 is 15.902 seconds (median 6.133; worst 20.706). Ordered-bundle worst is 21.020 seconds. OCR service median/P95/worst is 0.053/0.396/0.856 seconds. Capture-to-classification P95 is 20.015 seconds, although phase computation itself is cheap: this metric includes producer backpressure and overdue simulated capture.

Latest replay dispatch lateness P95/worst is 19.898/20.433 seconds. Internal frame backlog is bounded at four, with 26 queued jobs at peak, but scheduled input falls progressively behind. Processing takes roughly 1.90 times the clip duration; 2.637 fps cannot sustain 5 fps. No rejected frames or capture timestamp gaps appear in the saved runs because the replay producer blocks and eventually submits every frame. A real capture adapter must report upstream losses; bounded queues do not establish lossless live capture.

Original icon runs submitted/completed 599 jobs (495 OCR, 104 icon), with only one coalesced region. Latest no-icon run submitted/completed 349 OCR jobs and coalesced 147 regions. Summed latest OCR service is 40.316 seconds of 41.708 wall seconds, identifying OCR workload as the dominant current bottleneck. Original serial icon service totals 69.702 seconds; worker icon service totals about 93.4–93.6 seconds, with P95 around 1.89 seconds versus 0.695 serial. This is consistent with contention but does not isolate its cause. Worker overlap produces only about 2.5% throughput improvement in the original comparison. Whole-frame settlement, producer backpressure, and routine OCR demand propagate delay even with a separate message lane. The latest comparison changes both icon policy and field caching, so its improvement cannot be attributed to either independently.

## Highest-impact future work

1. Profile routine OCR by region and optimize measured crop/model cost. Evaluate recognition batching or a smaller backend against reviewed text/number accuracy before adoption. Latest OCR service demand must fall substantially to sustain capture cadence.
2. Evaluate field-specific scheduling/reuse on a larger annotated set, especially HP, status, and message changes. Preserve unresolved evidence and watermark dependencies; avoid scene-based deduplication or skipping short messages.
3. Profile/index icon matching and cache only justified identity evidence. Isolate icon and OCR CPU/thread contention in controlled trials before changing concurrency or creating model replicas.
4. Validate longer sustained paced/live capture, source loss reporting, transport latency, memory bounds, message recall, and decision completion distributions. Keep message delivery and all-required-evidence settlement separately measured.

No speculative optimization, M2 reconstruction, strategy, commit, or push was performed. Architecture correctness is validated within the supported observation scope; the configured **1-second processing target fails**, and production real-time readiness is not established.
