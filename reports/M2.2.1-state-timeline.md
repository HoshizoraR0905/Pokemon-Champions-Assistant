# M2.2.1 — Battle State Timeline Viewer

Generated from the existing M2.2 serialization and saved snapshots, without changing the state engine, decoding video, or running OCR.

Open `reports/M2.2.1-state-timeline.html` directly in a browser. It embeds all data, styling, and scripts; no server, network requests, external assets, or Python execution is needed to view it. Event 0 is the initial state; the next 20 entries follow the saved ordering. Buttons, the event list, and left/right arrow keys select an event. A persistent summary shows both sides' active positions and global conditions. The state panel includes benched/fainted Pokémon, HP units, unknown statuses, stages, items, abilities, and side effects. Changed Pokémon and global conditions are highlighted.

## Reproduce or reuse

```sh
.venv/bin/python scripts/export_m221.py
```

For another battle:

```sh
.venv/bin/python scripts/export_m221.py \
  --history /path/to/serialized-m22-engine.json \
  --snapshots /path/to/m22-state-snapshots.json \
  --initial /path/to/initial-context.json \
  --output /path/to/viewer.html \
  --json-output /path/to/timeline.json
```

`--initial` is optional; the default is the engine's serialized `initial_state`. It accepts the existing fixture wrapper or a raw state. History uses the existing M2.2 engine envelope, including event records, application statuses, and ordering. Snapshots use the existing `{"snapshots": [...]}` envelope and must represent chronological prefix states consistent with the history. Duplicate/missing snapshots, hash/status mismatches, incomparable ordering domains, and a mismatched final state fail explicitly. Unordered events, if present, are shown after ordered events in delivery order and retain their application status; this does not assert a chronological position for them. Arrival-order snapshots that became stale after replay/correction must be regenerated before export.

The exporter module is `tracking/state_timeline.py`; the buildless HTML template is `tracking/templates/state_timeline.html` and is included in package data. `reports/M2.2.1-state-timeline.json` provides a reusable structured export with full before/after states and raw field-level differences. Arrays are compared atomically to preserve ordered record context; dictionaries are compared by key. The HTML includes this same structured data.

## Change semantics

The prominent differences are derived programmatically from actual before/after snapshots, with gameplay, knowledge/evidence, and observation categories. Location/slot changes, HP endpoints, global effects, move execution records, and explicit stat-change records are gameplay transitions. Item/ability revelation and activation evidence, stage bounds, and knowledge classification changes are presented separately. Provenance-only updates, event IDs, party lists, vacancy lists, and tick bookkeeping are excluded from gameplay changes but remain visible in expandable raw differences and structured state.

A derived-to-observed reaffirmation of the same fainted value is a knowledge change. Creating a new instance does not imply activation of its empty history lists. Unknown facts remain unknown. The Special Defense change is shown as an increase with unresolved magnitude and initial baseline, rather than an invented exact stage.

“Observation-only” means no gameplay transition: the effectiveness and absorbed-electricity events still mutate the observation ledger. The viewer explicitly explains this distinction and retains both events, their source evidence, confidence, and original Chinese text.
