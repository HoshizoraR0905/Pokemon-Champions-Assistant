# M2.3.5-D — Battle 5 HUD and held-out failure diagnostic audit

Completed 2026-10-15. Investigation only; no production recognition, admission, state or label changes.

## Findings

**The dominant held-out loss is a combination of nickname/icon recognition, HUD observation scheduling, and a name/icon evidence-contract mismatch.** Camera-to-model association is not used by the audited runtime path and explains none of the measured failures.

Of 17 held-out species/slot checkpoint facts, three are supported currently. The fourteen losses separate into six unresolved nickname/icon identities, five visible-but-unscheduled HUD observations, and three correct Excadrill readings rejected after color-margin ambiguity. All six canonical species recognized at the three held-out HUD snapshots are correct; only three pass state admission. Every admitted one binds and remains current at its frame.

The three regressions therefore occur **before instance/slot binding**, not because correct admitted evidence is lost to freshness. The prior milestone report remains unchanged; this audit narrows its general “weaker icon support” explanation to an exact branch/serialization interaction.

## Precise cause of the three regressions

| Time (s) | Default Excadrill / runner-up | Default Δ | Color Excadrill / runner-up | Color Δ | Saved independent icon |

| 300.016667 | 0.89612 / 0.71776 | 0.17836 | 0.89754 / 0.79900 | 0.09854 | ambiguous: `small_species_margin` |
| 380.030000 | 0.89571 / 0.71844 | 0.17727 | 0.89691 / 0.79963 | 0.09728 | ambiguous: `small_species_margin` |
| 452.010000 | 0.89634 / 0.59873 | 0.29761 | 0.89772 / 0.79866 | 0.09906 | ambiguous: `small_species_margin` |

The first candidate stays Excadrill and its score **increases slightly** in all
three color results. The runner-up changes to Glimmora and rises to
0.79900/0.79963/0.79866. The strict “difference < 0.10” ambiguity set includes
these runners even though their individual scores are below the 0.80 winner
minimum. Thus this is a discrimination/margin problem, not a missing correct
candidate or low-confidence name transcription.

The decisive source path is:

1. `recognition/icons.py:76`, `IconRecognizer.identify`: apply winner minimum
   0.80 and cross-species margin 0.10; return the independent icon as ambiguous.
2. `recognition/identity.py:6`, `combine_identity`: when text is resolved and the
   icon is ambiguous, filter icon candidates by the text species. An eligible
   candidate ≥0.80 with a unique variant can yield a local `replace(icon, ...)`
   marked resolved, then produce a text observation whose method is
   `text_icon_agreement`.
3. `scripts/finalize_m235.py`, `prepare`: serialize the original independent
   `icon` separately, then serialize the returned combined text. The local
   replacement icon is not returned to this caller. The resulting receipt has
   `species.resolution.method == 'text_icon_agreement'` but
   `icon.status == 'ambiguous'`.
4. `tracking/evidence_fusion.py:15`, `identity_evidence`: the agreement branch
   requires the saved icon to be resolved; it fails. The independent exact-name
   branch requires `method == 'exact'`; that method was overwritten. Even name
   confidence 1.000 does not reach it. The result is
   `identity_not_independently_supported`.
5. `hud_transition` records the raw HUD then returns before instance selection
   or HP attribution. `recorded_observation` is evidence retention, not admission.
   There is no failed `_resolve` call, side disagreement or slot collision here.

This is an evidence-contract interaction classified as
`admission_threshold_failure`, with `icon_matching_failure` (margin) and `other`
(fused-method/serialized-status mismatch) as contributing causes. Merely
increasing OCR confidence would not fix it. Passing the text-filtered icon off as
independent corroboration would erase provenance and risk circular confirmation;
that is not a recommended fix.

The saved default replay admits these views and assigns current episodes. At
380.03 and 452.01, baseline reuses its earlier Excadrill instance while the saved
v2/default replay creates new observed episodes after gaps. Both still supply the
correct **current species/slot**. This distinguishes successful present-frame
identification from unresolved biological continuity. The default replay remains
unversioned evidence; no new controlled replay was run.

## Exact admission rules

These are engineering heuristics, not calibrated probabilities or game mechanics.
Source references are the unchanged current files pinned by the implementation
seal; the source hash inventory is in the diagnostic JSON.

| Gate | Existing rule | Effect in this audit |
| --- | --- | --- |
| Raw HUD identity | Resolution must be `resolved`, species present, OCR ≥0.75; conflicting text/icon species or variants are rejected | Nickname OCR can be excellent while canonical resolution remains unknown |
| Literal exact name | Unique dictionary species, resolution confidence `strong`, method `exact`, normally OCR ≥0.95; weaker readings may use existing repeated/prior named support | Tyranitar passes without a resolved icon; no universal independent-icon rule exists |
| Combined agreement | Method `text_icon_agreement` **and independently saved icon resolved**, same species | Three color Excadrill views fail here |
| Independent icon | Winner ≥0.80; every candidate within strict <0.10 must agree on species and variant; unmapped candidates also block resolution | Sub-minimum runners can still veto a winner |
| Nickname | Method `icon_only`, noncanonical raw nickname, OCR ≥0.95, resolved matching icon with top score ≥0.85, plus a repeated observation or opt-in high-margin support | No Battle 5 opponent nickname meets this gate |
| Opt-in high-margin nickname | At least two candidates; winner ≥0.90 and top-two gap ≥0.20 | Lowering only the icon matcher's minimum is insufficient for nickname admission |
| Text-filtered variant | In `combine_identity`, eligible same-species candidate ≥0.80; variants within <0.10 must be unique | This is conditional on text and must remain distinct from independent icon evidence |
| HP | Valid numeric value, confidence ≥0.75, and identity admitted before HP state update | All saved snapshot HP readings are usable numerically; rejected identities keep them unbound |
| Current occupancy | Location directly supported at `as_of`, no later relevant coverage gap, no conflicting/deferred latest HUD or pending unplaced arrival | All admitted held-out same-frame HUD observations remain current |

The 30-second prior named-corroboration window and repeated-name rules also remain
unchanged. No threshold was modified for this task.

## Dynamic Camera and HUD/3D Coordinate Assumptions

The camera can change rendered scene geometry while UI identity remains directly
observable. Three systems are kept separate in this audit:

| System | Evidence represented | What it does not establish |
| --- | --- | --- |
| A. HUD identity | Literal UI nickname/species, 2D UI icon, HP, UI crop coordinates | A nearby 3D model's identity, a biological individual across gaps, or a model that is off-screen |
| B. Logical battle position | Self/opponent, logical active slot, observed instance episode and evidence-backed transitions | Screen-space position, foreground/background, or camera orientation |
| C. Rendered 3D scene position | Screen coordinates of an on-screen rendered model at this frame | Side/slot from proximity, a switch/faint from disappearance, or an animation actor without independent evidence |

**Confirmed code assumptions and evidence paths:**

- `recognition/__init__.py:38`, `classify`, and `Recognizer.recognize:109` use
  fixed **HUD UI** regions and card colors. Own-name/icon/HP regions lie toward
  the bottom left; opponent UI regions toward the upper right. `own_active_1/2`
  and `opponent_active_1/2` index these UI elements. This is a fixed UI-layout
  assumption, not a fixed camera orientation or body-position assumption.
  The both-sides screen gate explains why a partial single-HUD frame can be
  missed. The anchor rule in `scripts/process_m235.py:98`,
  `recognize_baseline`, separately limits HUD invocation frequency.
- `recognition/icons.py:76`, `identify`, receives the saved **UI icon region**.
  Candidate `location` and `scale` are template-alignment coordinates inside a
  resized UI crop. They are not positions of rendered scene models. Background
  color estimation is local to that crop, not a player/opponent camera model.
- `scripts/replay_m233a.py:54`, `events_from_cache`, maps UI slots ending in 1/2
  to logical left/right, and own/opponent prefixes to battle sides. This
  provisional UI-index-to-logical-slot mapping is a real assumption requiring
  layout-specific validation. It does not select the nearest 3D model. Frozen
  labels agree with the admitted side/slot results in this sample; no admitted
  wrong-slot result was found.
- `tracking/evidence_fusion.py:73`, `hud_transition`, binds from the event's
  side/slot, canonical identity, previous observed episodes and explicit
  continuity. It has no 3D coordinate input. `prepare_message:236` binds message
  actors from current HUD-supported context; it does not use animation position.
- `recognition/visual_adapter.py:8`, `selected_panel_side`, maps highlighted
  **UI selector** positions to sides, not active slots. `visual_events:25` and
  `tracking/reliability.py`, `visual_transition`, bind panel/banner species on
  an observed side, not a nearby model. `recognition/visual_evidence.py`,
  `popup_regions`, assumes self/opponent **banner UI** locations. The party-panel
  adapter identifies an own-party UI row and explicitly does not supply a field
  slot. These UI mappings are provisional and should not be repurposed for 3D.
- `tracking/state_engine.py:230`, `_resolve`, resolves explicit instance IDs or
  unique species among active instances on a known side. `_transition:266`
  processes explicit send-out/withdrawal/faint events; it does not monitor model
  visibility. `tracking/__init__.py`, `Tracker.update`, compares non-null
  observations and ignores missing values; model disappearance is not an input.
  Its `species_change` observation is not a camera-derived switch event.
- `battle_events/parser.py`, `EventParser.parse`, uses text, existing aliases,
  side hints and prior chronological context. It does not infer the actor from
  an animation's screen position. `tracking/evidence_projection.py:13` uses
  provenance times, gaps and state facts, without 3D geometry.

No nearest-model lookup, body detector, 3D tracking association, fixed
foreground/background participant mapping, or “disappeared model ⇒ switch/faint”
path was found in the inspected recognition→HUD event→fusion→StateEngine path.
This is a scoped code finding, not a claim about uninspected future integrations.
A fixed HUD mapping is present; treating it as a fixed 3D mapping would be an
unsupported reinterpretation of its data.

**Effect on evaluated errors:** camera movement is not a confirmed root cause
for any of the seven saved snapshot results or any of the seventeen held-out
facts. For the three regressed views, the exact loss is fully explained by saved
scores and the admission contract; a 3D association is irrelevant to that branch.
For missing HUD observations, the observed cause is screen/anchor gating. A
changing scene might affect a broad color/glyph phase heuristic, but this audit
has not isolated that effect and does not attribute scheduling misses to camera
rotation. Crop clipping is a UI-region issue, not proof of camera motion.

**M2.3.6 implications:** a camera estimator or 3D-to-HUD association is not needed
to fix these demonstrated HUD failures. Future work should preserve independent
HUD identity and logical-instance provenance, validate UI layouts including
partial HUDs, and treat optional 3D detections as a separate observation stream
with unknown associations by default. Any later cross-stream link must carry
independent evidence and uncertainty; proximity, screen motion or disappearance
alone cannot change active occupancy or reveal an actor.

### Recommended future design for M2.3.6

Keep three independently evidenced records rather than one merged identity:

1. **Preview roster observation:** battle/source identity, side, preview UI row,
   frame hash/time, layout, icon candidate species/form, uncertainty and source
   references. Reuse canonical `KnowledgeBase` IDs. Preserve member occurrences
   and duplicates; do not use a set as proof of individual identity or complete
   selected party. A preview row is not a logical active slot.
2. **Displayed-name association:** preserve the exact raw nickname plus a
   deliberately normalized lookup key, species/form claim, supporting same-card
   icon or explicit linked revelation, and conflicting alternatives. Scope it by
   battle and side, and by instance where established. Roster membership is
   contextual evidence only, never the sole alias-admission reason. Independent
   icon evidence must remain distinct from roster/text-conditioned ranking.
3. **Observed active episode and persistent instance:** bind an admitted HUD's
   identity/HP to a logical side/slot at its observation time; separately record
   switches, explicit continuity, retractions and gaps. Species equality, nickname

source-backed evidence where necessary; do not create a hardcoded Battle 5 alias
map or a competing identity database. Acquire a new independent evaluation set
before testing these changes. This task implements none of that pipeline and
