# M2.2.4 — Knowledge-grounded initialization and transitions

## Outcome and scope

The existing StateEngine now accepts evidence-backed own-team configuration and a versioned mechanics knowledge layer. It replays the same 196 cached M2.2.3 events through the existing transition path. The default remains `champions-evidence-only-v1`; a second, explicitly requested `--provisional` export demonstrates quantitative simulator-reference effects. Both exports preserve all 28 independent HP checks, 28 identity checks, and every prefix's current HP, displayed percentage, active/bench location, and faint state. No video decode, OCR, annotation extraction, damage calculation, hidden-state inference, or recommendation engine was run or added. The original M2.2.3 artifacts and saved team were not overwritten.

## Mechanics knowledge and causal policy

`data/move_mechanics_v1.json` contains canonical move IDs, bilingual names from the existing identity layer, categories, targets, stage deltas, timing, success requirements, preconditions, exceptions, rule IDs, profile applicability, provenance and verification labels. Coverage is deliberately small: Swords Dance, Close Combat and Electro Shot from the recording, plus Dragon Dance, Calm Mind, Iron Defense and Growl fixtures. A separate passive-rule entry supports the observed Stamina activation/result sequence.

All eight numerical rules are **provisional for Champions**, using the pinned [Pokémon Showdown move implementation](https://github.com/smogon/pokemon-showdown/blob/3a766f2cfb5e51c1e428cfe87d0dba91a8f01640/data/moves.ts) and [ability implementation](https://github.com/smogon/pokemon-showdown/blob/3a766f2cfb5e51c1e428cfe87d0dba91a8f01640/data/abilities.ts). These are primary simulator sources, **not official Champions rules**. No new numerical rule is claimed independently Champions-verified. Rules apply only to `showdown-champions-reference-v1`; the evidence-only profile cannot query them. Exact numeric deltas and replacement stages supplied by direct observations remain supported in evidence-only mode.

A move announcement records an uncertain outcome and expected rule, without applying a boost. A compatible observed stat-result message for the same instance confirms the effect and applies it once. Automatic association is limited to the latest uninterrupted action; turn boundaries and intervening ability/item/entry observations prevent carrying an unrelated expectation forward. Explicit `effect_of` action IDs disambiguate result messages. A directly confirmed execution can apply an effect only with explicit `effect_outcome='confirmed'` and `interaction_checked=True`; matching linked results corroborate rather than add another delta. `selected`, `failed`, `blocked` and `uncertain` outcomes do not generate numerical effects from execution alone. An observed failed/blocked `move_effect` can update an explicitly linked action's outcome.

Each effect receipt includes the action observation, result observation, rule and source, active profile, verification label, previous stage, nominal delta, and exact/bounded resolution. Separate effects of one action are keyed by stat. Separate independent actions remain separate even within one turn. Explicit duplicates attach corroborating evidence. An unlinked repeated outcome is kept as ambiguous evidence: the stage range includes both corroboration and another change, without assuming an extra boost. Orphan result messages remain usable direct observations. If the direct magnitude conflicts with a rule, both are retained; an already applied associated generated delta is replaced by the direct result from its recorded baseline rather than counted as another boost.

Unknown starting stages remain unknown with bounded relative updates, e.g. `[-6,6] + 2 → [-4,6]`. Exact known baselines use the engine's existing [-6,+6] bounds. This is local stage representation already present in M2.2, not M2.3 hidden-state tracking. The knowledge layer is replayed in trial states, so rejection rolls it back with the transition. Existing correction, retraction, duplicate-delivery and serialization paths reconstruct associations deterministically.

## Remaining limits

Opening data is a manually inspected fixture, not an automatic new recognition pipeline. Provisional rules cannot prove their Champions applicability. General opponent/group/ally mechanics, delayed or interrupted action association, comprehensive item/ability effects, and game-specific interaction coverage remain outside this milestone. Automatic association intentionally defers complex evidence rather than guessing. The replay supplies exact direct stage observations when available but does not calculate effective battle stats, damage or Speed. Unknown configurations stay unknown.

The timeline reconstructs complete before/after snapshots from a compact shared-node transport. Default-browser opening is not a visual layout audit. Seven expensive unrelated OCR/video tests are excluded using the same deselections documented in M2.2.3. No commits or pushes were made.


## Timeline loading optimization

The HTML export now uses `interned-timeline-v1`, a lossless transport that stores identical configuration, evidence, lists and state subtrees once. States reference shared nodes; the viewer decodes them into shared read-only objects. The original timeline semantics and separate state/snapshot JSON files remain unchanged. The Python `unpack_timeline` helper and browser decoder also accept the previous plain timeline payload. `build_timeline` and standalone timeline JSON exports keep their existing schema.

| Export | Before | After | Reduction |
| --- | ---: | ---: | ---: |
| Conservative | 186,692,505 bytes (178.0 MiB) | 1,470,677 bytes (1.40 MiB) | 99.21% |
| Provisional | 241,910,506 bytes (230.7 MiB) | 1,527,978 bytes (1.46 MiB) | 99.37% |

Both exports were decoded and compared against every original state, difference and provenance record: all 197 entries are equal. Optimization reuses the saved HTML data and does not replay the battle or rerun media recognition. Rendering now defers full state/debug, causal knowledge, configuration provenance and mechanic provenance JSON until their details panel is expanded. Open panels refresh on navigation; collapsed panels do not serialize those records.

The offline Node DOM smoke test navigated all 197 entries in both real exports, verified deferred debug rendering and exact last/first state display when the debug panel is open. Script initialization was 34.26 ms (conservative) and 26.62 ms (provisional); all-entry navigation plus lazy-debug verification was 49.28 ms and 45.13 ms. These are minimal-DOM script timings, not real browser layout or end-to-end file-open measurements. Both refreshed local HTML files were opened successfully with macOS `open`.
