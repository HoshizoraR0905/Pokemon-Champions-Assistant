These durations overlap and must not be summed. State replay contains parser and W work; reconstruction/export contains adaptation, replay, serialization and HTML generation; OCR calls can be children of region/W work. Decoder timing measures time spent awaiting the next sampled frame. FFmpeg executes concurrently and blocks behind the consumer, so pure decoder CPU/wall time is **not isolated**. A 2.077-second wait is not a claim that the whole video decoded in that time.

Lazy OCR initialization, general UI work, scheduling outside W, source/input hashing, frame/JSON writes and untimed Python work are included in broad elapsed intervals but are not all separately isolated. The startup residual also includes process exit/printing and up to five seconds of monitor polling tail; pure startup alone was not isolated. RSS is sampled every five seconds over the child and descendants, so actual instantaneous peak can be higher. Post-seal saved replay, report rendering, browser checks and regression tests are separate from production timing. All timer call counts and inclusive/exclusive definitions are in the JSON metrics.

The measured run is slower than real time; the existing internal duration-plus-five-seconds target was not met. This is one observed run with instrumentation, not a cache-reuse performance improvement or an uninstrumented hardware benchmark. Icon matching is the largest measured inference interval.
