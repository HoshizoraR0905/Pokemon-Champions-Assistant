## Prediction and independent comparison protocol

Existing message and trainer events alone drive a separate instance of the established occupancy/episode engine. Literal send-out names are mapped without fuzzy matching, roster-order assumptions or HUD aliases. The prediction file is written before the comparison reads HUD identities. Side and slot come from the message-only prefix; a later HUD cannot repair either field. The known double-opening ordering convention is inherited, not newly validated across layouts.

The second phase selects the first subsequent fresh, independently accepted HUD in the same side and slot, bounded by message-only departures or later same-slot arrivals. It uses the existing independent evidence policy with no message support argument or roster conditioning. The six selected confirmations use text/icon agreement or literal-name/independent-icon agreement. Their name OCR regions were fresh, not individually reused. All candidate/rejection records, source IDs, image hashes, timestamps and title provenance are retained in `comparisons.json`. Unknown slots prevent a scored comparison even when the HUD-assisted production replay later places that Pokémon.

## Verified titles and overlapping species names

The scoped source is [52Poké: Pokémon titles](https://wiki.52poke.com/zh-hans/称号), revision **2597624**, retrieved **2026-10-19**, with its Champions-specific discussion. This is the Pokémon ribbon/mark title article, rather than the similarly named Champions trainer-achievement article. Source attribution, game applicability, raw-HTML hash and CC BY-NC-SA 3.0 licensing are recorded in `knowledge/data/52poke_titles_v1.json` and `NOTICE.52poke-titles.txt`.

The offline supplement contains 112 numbered rows and 111 supported static strings. The variable original-trainer-name template is unsupported. Explicit Champions wording is selected where the article distinguishes it. Missing titles remain unsupported; the snapshot does not assert a universally complete game vocabulary. The parser validates the actual table headings, row coverage and duplicate consistency. Reproduction uses the retained HTML via `scripts/snapshot_pokemon_titles.py`, without fetching the site again.

`knowledge/message_names.py` resolves identities through the existing canonical `KnowledgeBase` and parser. It tries a complete name, or one complete documented title followed by a complete canonical name. It does not scan arbitrary suffixes. Every successful decomposition must agree; competing identities cause abstention. Consequently `开始犯困的超能妙喵` resolves to Meowstic (678), while `开始犯困的妙喵` resolves to Espurr (677). Unknown prefixes, incomplete names, stacked titles and typos stay unmapped. Tests cover both names and a deliberately conflicting title decomposition. Forms are asserted only when the existing identity database uniquely supports them. No live network is required at runtime.

The helper is used by the offline experiment. Existing production parsing, HUD recognition, models and W verification are retained unchanged.

## Separate reusable own-team profiles

The existing `TeamConfiguration` v2 collector, manual corrections and provenance remain authoritative. `team_configuration/profiles.py` adds a local build registry; `scripts/team_profiles.py` exposes registration, listing and export. A build must have six distinct ordered configuration slots, all required fields manually verified, valid canonical IDs/numeric values and no unresolved conflicts. An imported `complete` flag is insufficient. Unverified optional fields are reset to unknown in the registered copy; the source configuration is unchanged. Existing profile IDs cannot be silently replaced; publication is atomic. Retrieval verifies the stored configuration hash and returns a separate configuration object.

No real team was registered from incomplete Battle 9 evidence. The cache is independent of display-name matching and persistent profiles contain no battle state. Choose distinct profile IDs for different builds sharing the same species roster:

```sh
.venv/bin/python scripts/team_profiles.py register sun-build-a --configuration data/teams/verified-sun-a.json --reviewer trainer
.venv/bin/python scripts/team_profiles.py register sun-build-b --configuration data/teams/verified-sun-b.json --reviewer trainer
.venv/bin/python scripts/team_profiles.py list
.venv/bin/python scripts/team_profiles.py export sun-build-a --output data/teams/selected-sun-a.json
```

The default registry is `.cache/team-profiles/`; `--directory` selects another persistent local location. Collect/review configuration with existing `main.py --collect-team`, `--team-out` and `--team-corrections` options before registration. Export is TeamConfiguration **v2**, not the legacy `--verified-team` v1 format. Programmatic consumers can use `TeamProfiles(...).load(profile_id).data` with the established `tracking.knowledge_grounding.initialize_team` path, retaining explicit verified same-individual bindings and `saved_match_verified=True`. Species-roster coincidence never selects a build or binds members automatically. Event-driven production still has its existing team-option restrictions; this task does not inject profiles into the untouched first pass.
