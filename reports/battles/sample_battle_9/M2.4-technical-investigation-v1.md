# M2.4 technical investigation: COMMAND_TIME, withdrawal and extensibility

Investigation date: 2026-10-19. Scope: maintained M2.4 only; findings and proposals for review. No production recognition, sampling, identity policy or state semantics changed. No video decoding, OCR inference, acquisition, full replay, M3 work, commit, push or cache deletion was performed.

The two COMMAND_TIME totals reconcile to the saved measurements. Decoder/sampling waits and delayed state reconstruction dominate; OCR model inference contributes **zero** in these warm-cache runs. The Pelipper withdrawal fails **before OCR, at the short-message visibility gate**. Future move-interface observations fit the existing architecture, but committing an action requires independent evidence beyond a highlight or menu disappearance.

## 1. COMMAND_TIME cost audit

### Inputs and accounting boundaries

The primary inputs are `m24-lightweight-final-v1` and `m24-development-final-v1`, under `.cache/battles/sample_battle_9/{event-driven,evaluation}/`. Their existing `execution.json`, `profiler/segment-0000/{operations,frames}.jsonl`, `profiler.json`, observations and M2.4 `segment-performance.json` were read. Measured output/profile hashes were checked against `execution.json`; all passed. The two runs have the same 15 COMMAND_TIME segment boundaries, covering **114.55333333333334 video seconds**. This is the existing heuristic phase partition, not independently annotated phase accuracy.

The complete **30-row segment timing table, per-segment component tables, per-purpose OCR tables, and top ten segments for each mode** are in [COMMAND_TIME segment tables](M2.4-command-segment-tables-m24-technical-audit-v2.md). The detailed JSON retains both inclusive and exclusive module timings, counters and input SHA-256 identities:

`.cache/battles/sample_battle_9/evaluation/m24-technical-audit-v2/cost-audit.json`

The reported wall number is a **source-video attribution**, not a stopwatch started when a command screen appeared and stopped when it disappeared:

1. Each candidate's acquisition-consumer wall is assigned by its actual source PTS timestamp to a half-open segment `[start,end)`.
2. The main-thread `next(decoded_frames)` span is assigned to the candidate it returns. This includes waiting for bytes and metadata, reading/assembling the raw image, and generator work. FFmpeg runs concurrently; its CPU time, scaling time and OS scheduling waits are not separately measured. The source decoder visits all video frames before selecting 2 FPS candidates.
3. Post-acquisition `adapt_frame` and final-replay `state_event` inclusive spans are assigned to their originating source timestamps. Consequently a COMMAND_TIME segment includes work executed much later, during reconstruction. It does not mean that live command processing repeatedly replayed that state.
4. Model initialization and genuinely shared work remain shared under the maintained report policy. Parent process launch/monitoring/exit-poll overhead also remains outside these segment totals. None of that shared residual is arbitrarily redistributed here.
5. Nested inclusive timers cannot be added. `ocr_read` contains preprocessing and `ocr_predict`; `state_event` contains `state_hash` and transitions; development verification contains its OCR/icon calls. Exclusive bodies subtract child spans, including measured child recording overhead. Frame wall includes instrumented and uninstrumented work plus profiling perturbation.

This investigation also groups acquisition operations by their **monotonic enclosing frame**, rather than blindly using each nested operation's source timestamp. Development prefix replays refer back to older evidence: their `adapt_frame` / `state_event` source-module totals can appear in earlier command segments even though their execution occurs inside a later non-command frame. The maintained wall allocation correctly excludes those nested roots. For example, raw development command-source `state_event` spans sum to 13.155982s, but only **12.841254s** belongs in the disjoint delayed-state column. Raw adaptation is 0.247391s; the disjoint delayed adaptation is **0.023139s**. Summing the original module columns would double count verification work.

### Avoidable-work assessment

- **Repeated recognition:** warm command model inference is already eliminated. Repeated cached API requests remain: 101 field-label reads with no region reuse, 113 countdown reads and 558 HP reads; repeated detail views produce 210 variant cache lookups. Their measured API time is small here. Cold-cache relevance requires a scoped future measurement; this pair cannot establish its savings.
- **Unchanged frames:** command inspection already drops 109/229 candidates, while always checking UI at 2 FPS. Full frames all differ, often because the arena animates. Whole-frame deduplication would therefore miss the relevant reuse opportunity. Fifteen HUD region decisions already reject unchanged regions; changed-card signatures still trigger reads even when individual HP text reuses. A future field-level gate should preserve HP changes and message appearance rather than equating stable UI with no new evidence.
- **Full-state replay:** lightweight acquisition does not replay state each frame. Packaging builds all event records and performs **one final 593-event replay**. It hashes/deep-copies growing state per event; 371 final event spans are attributed to command segments. Development also performs **11 prefix reconstructions**, 19.628599s inclusive across the entire video, triggered by relevant message/trainer changes. Their enclosing triggers are outside COMMAND_TIME. They rebuild message-only evidence by adapting the prefix and replaying filtered events; this is a real development overhead, but cannot explain the lower command total. No proposal should substitute repeated `StateEngine.apply()` for batching: `apply()` itself invokes full replay.
- **Image saving:** 120 PNGs and monitor/observation/checkpoint writes provide auditability and recovery. Their volume warrants instrumentation, but the existing profile cannot prove they dominate the 6.1s remainder. Selective or asynchronous saving would need durable evidence/provenance and interruption guarantees before acceptance.
- **Repeated UI work:** all 229 candidates run broad UI classification/region checks. W detection on inspected frames can independently repeat card/overlay inspection. There is a bounded reuse opportunity, but no measured time for that duplicated subset; the entire UI/W measured span is only an upper bound.

## 2. Missing Pelipper withdrawal near 294s

### Earliest failure and evidence chain

**Root cause: visual message selection rejects a legitimate short two-row message. It is not a missing sampled frame, ROI clipping, demonstrated OCR error, aggregation error, parser error or StateEngine binding error.** The distinction matters: expanding this particular ROI alone would not remove the failing minimum-stroke requirement.

Original adequate evidence exists. The [294.000s saved frame](../../../.cache/battles/sample_battle_9/event-driven/m24-lightweight-final-v1/frames/000476.png) visibly shows `大嘴鸥，` on the first row and `回来！` on the second. The 294.5s, 295.0s and 295.5s saved frames also contain the message. No video reacquisition was needed. The same empty-message outcome appears in original sealed `m239-message-baseline-v1` and both final M2.4 runs.

| Stage | Observed evidence / result |
| --- | --- |
| Source sampling | Actual timestamps 294.0, 294.5, 295.0, 295.5s; integer PTS 176400, 176700, 177000, 177300; time base 1/600. All four frames were inspected and saved. This is adequate evidence at the original sampling rate. |
| Broad phase classification | `battle_animation`, confidence 0.61; its glyph-count threshold does not identify this short message. Broad phase is not the final live-message admission gate: `fast_profile.inspect()` evaluates local message geometry independently. |
| ROI / line geometry | Fixed ROI `[288,413,839,481]`. At 294.0s, detected fragments `[289,414,366,439]` and `[290,451,344,476]`; row read boxes would be `[289,411,366,443]` and `[290,444,344,478]`. Both complete lines are inside the native image and their visible glyphs inside the ROI. There is no observed clipping of the species or recall text. |
| Visibility gate | `features().text_geometry=False`; `fast_profile.inspect()` labels message `partial`, not `visible`. Its `message_visible` is false. Native geometry and text exist, but the selector does not accept them. |
| Region selection / OCR requests | `fast_video.analyze()` takes `uncertain_visibility`, records empty raw text and does **not** call `read_message`. No battle-message OCR request or raw OCR output exists for these four frames. Unrelated field OCR around this interval does not constitute a withdrawal read. |
| Multi-frame occurrence aggregation | Each row has `selected=False`, `visibility='partial'`; `MessageOccurrences.observe()` returns `no_visible_live_message`, no event. Partial visibility can retain dedup context but supplies no reading/overlap to assemble. |
| Parsing control | A diagnostic call to the existing parser with manual text `大嘴鸥，\n回来！` yields `switch_out`, side `self`, canonical species 279, no uncertainty. This establishes grammar support only; the supplied text is manual, not an automatic OCR success. No parser call receives that text in production here. |
| Adaptation / binding | `video_events()` has no withdrawal candidate to adapt. Final history has no Pelipper `switch_out` at 294s; StateEngine cannot bind or reject an event it never receives. The downstream occupancy gap is the consequence, not the earliest failure. |

The exact failing selector is `recognition/message_selection.py::features`, called by `recognition/fast_profile.py::inspect`. Default `SelectionConfig.minimum_strokes=4` and `minimum_span=50` require at least four character-like contour components aligned on **one baseline**. At 294.0/294.5s the first row's candidate groups contain three components spanning 63px. The second row's groups contain two spanning 40px; punctuation components do not form a qualifying group. At 295.0/295.5s the largest first-row group is still three components, spanning 66/64px. Thus no row meets the conjunction. Counts of contours are not counts of Chinese characters: connected or fragmented glyphs also affect the gate.

Geometry was recalculated on saved pixels with the maintained pure-CV function; the function's return locals were inspected to retain candidate-group receipts. No thresholds or runtime code were changed. Saved source fingerprints for `fast_profile.py`, `message_selection.py`, and `ui_regions.py` match the inspected implementation in both the final Battle 9 run and the cited Battle 8 run. Detailed receipt:

`.cache/battles/sample_battle_9/evaluation/m24-technical-audit-v2/withdrawal-geometry.json`

The saved replay applies the 228.521667s Venusaur recall and 232.021667s Pelipper send-out to self/right. The missing 294s recall leaves no evidenced vacancy. ### Comparison with Battle 8 and correction to the earlier diagnosis

The [Battle 8 audit](../sample_battle_8/M2.3.9-deferred-and-uncertain-event-audit-v1.md) and its `unemitted-message-audit.json` independently documented the Charizard recall as a **left-shifted ROI miss** at 279.013333s. That historical assertion is preserved. However, inspection of its cited [original frame 000476](../../../.cache/battles/sample_battle_8/event-driven/m239-production-first-pass-v1/frames/000476.png) does **not support the clipping explanation**: `喷火龙，` and `回来！` are fully visible near x=290 within the same `[288,413,839,481]` ROI. Its saved fragments are `[290,414,366,439]` and `[290,451,344,476]`.

An independent recalculation gives `text_geometry=False`, no Battle Log overlay, and candidate groups of at most two components (one group spans 63px). It fails the same four-component baseline threshold. The current evidence supports a common short-message visibility failure for **these two cited frames**, rather than the earlier reported geometric displacement. This is a correction to the diagnosis, not a rewrite of the historical acquisition or acceptance result. It does not rule out genuine alternate-position/clipping cases elsewhere; none was demonstrated by the cited Battle 8 frame.

### Minimal general fix proposal and regression design — not implemented

Introduce a bounded short-message OCR opportunity when native line geometry supplies small, left-anchored, baseline-consistent text inside the live-message region, even if the ordinary single-row stroke threshold fails. Corroborate across the two known row bands or a stable adjacent frame; retain overlay, flash and arena-clutter rejection. Select the opportunity visually, then let actual OCR confidence, complete grammar and normal binding policy determine whether an event exists. Do not whitelist Pelipper, Charizard, battle IDs or timestamps, and do not manufacture a withdrawal from a later arrival.

The localized changes would be in `message_selection.py` / `fast_profile.py`, with row extraction reused from `ui_regions.py`. First evaluate a short-row candidate policy on fixtures; a global reduction of `minimum_strokes` without negative examples is insufficient. ROI expansion is a separate conditional change only if new evidence demonstrates clipping. If OCR from the correct rows later fails, retain that raw failure and address it separately.

Proposed acceptance fixtures and checks:

- Small curated native crops/full-frame references for Battle 9's four recall frames and Battle 8's cited recall, preserving source PTS, SHA and manual text labels. Add distinct short species/name rows and punctuation/line-wrap variants; keep at least one held-out recording/example.
- Negative frames: arena highlights/rain, flash, menu and target overlays, historical Battle Log text, partial reveal, one/two stray bright contours and unsupported resolution. Measure extra OCR opportunities and false admissions explicitly.
- Selection tests must show an actual OCR opportunity with uncut boxes. Stubbed row OCR tests should preserve the two rows, then feed the real occurrence/parser/adapter chain and assert one self withdrawal, no duplicate across repeated frames or scroll changes.
- A small synthetic state sequence: supported self/right Pelipper entry → supported recall → Archaludon entry. Assert departure before replacement, stable instances/revealed moves, idempotent replay, correction/retraction behavior, and no cross-battle leakage. Keep the existing missing-recall behavior as a negative case; absence of evidence must still prevent inferred placement.
- Only after selection passes, run narrowly scoped OCR on retained row crops in a new diagnostic namespace and inspect raw outputs. Do not regenerate either sealed acquisition. Portable fixtures should not require the original optional videos.

No major StateEngine, database or acquisition rewrite is needed to add **observations**. The main localized design work is a transient command-session reducer and safe actor binding. Reading a committed action is a separate evidence problem that may remain unresolved from these screenshots. A limited shared extraction of already duplicated row geometry would help; broad consolidation of the streaming and event-driven pipelines is unnecessary.

### Required semantic distinctions

| Observation | What may be recorded | What it must not establish |
| --- | --- | --- |
| Visible move list | Literal name, canonical move candidate, screen row index, observed current/max PP, visibility and confidence per field | Equipped slots for an unresolved actor; a move being chosen, executed or legal under every rule |
| Highlighted move | Candidate row/highlight appearance at source time, including ambiguity/multiple highlights | A click, a confirmed choice, target or PP expenditure |
| Selected Pokémon / slot | UI-selected acting subject and its independently evidenced binding to an existing player instance/entry episode | That party-list order equals active slot; that current highlight belongs to the previous actor after navigation |
| Target-selection view | Candidate target highlight, displayed move banner and card labels; bind target only with sufficient evidence | That target was confirmed or that the move later affected it |
| Explicit committed action | A documented visible confirmation/locked action receipt or other independently available confirmation signal, retaining revision/cancellation history | Commitment from a menu disappearing, a new actor prompt, a timeout, or phase transition alone |
| Later battle execution | Existing message-backed `move_execution` evidence, with actual actor/move and supported target/effect evidence | That an earlier highlight was committed; selection may have changed, been canceled or never executed |

If the interface provides no persistent confirmation signal and no input telemetry is available, report **commitment unobserved**. Target selection can support an intended candidate but not global final commitment. Do not add controller/input hooks or invent confirmation semantics to fill this gap. Link later execution to earlier candidates only as a separately evidenced relationship; do not backdate commitment or replace execution provenance.

### OCR budget and sampling adequacy

Use visual menu/actor/target signatures first; cache names per validated actor/menu session and PP separately. A static menu should need one bounded text-reading attempt, with a bounded retry only after unreliable evidence genuinely improves. Highlight motion is cheap CV; a new target screen needs only its new relevant fields. Foreground signatures should exclude the animated arena, countdown and highlight border from move-name invalidation while preserving an unknown-pixel fallback. Resume must retain enough scheduling state to avoid re-reading an already completed menu. Reuse is conditional on source/model/adapter/layout versions and menu/actor identity, not merely a similar screen.

**1–2 FPS is adequate only for persistent screens whose dwell time exceeds the actual sampling gaps; it cannot guarantee a short confirmation interaction.** At 2 FPS the nominal gap is 0.5s (actual selected PTS can drift by a source-frame interval); detailed command inspection normally has gaps around 1s. A 100–300ms confirmation/highlight can fall entirely between original materialized samples. A transition watcher at 2 FPS cannot recover a transition never sampled. For a future requirement, measure confirmation dwell and the longest actual sampling gap on a scoped interaction fixture. Consider a higher-rate visual-only command ring buffer or explicit confirmation signal, then select a small number of OCR frames independently.
